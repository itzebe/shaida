# Dataset methodology

This document describes exactly what data SHAIDA is evaluated on, where it came from, and what
it may and may not be used to claim. It is written so that a judge can reproduce every number in
[`RESULTS.md`](RESULTS.md) and can see where our knowledge stops.

## 1. Where the data came from

Every dataset used in this evaluation is either **provided by the organisers** or **generated by
us and clearly labelled as synthetic**. No real election data, no real voter data, and no scraped
personal content is used anywhere in this project.

| Dataset | File | Origin | Nature |
|---|---|---|---|
| Result records | `data/official-synthetic/results_synthetic.csv` | Official Rise Networks #AI4Elections synthetic starter pack | 900 synthetic polling-unit result records |
| Anomaly labels | `data/official-synthetic/anomaly_labels_HELD_OUT.csv` | Same official pack | One label per record |
| Incident reports | `data/official-synthetic/incident_reports_synthetic.csv` | Same official pack | 400 synthetic incident narratives |
| Claims archive | `data/official-synthetic/misinformation_claims_synthetic.jsonl` | Same official pack | 300 synthetic claims |
| Polling units | `data/official-synthetic/polling_units_synthetic.csv` | Same official pack | 900 synthetic unit records |
| Demonstration reports | Created by `scripts/seed_demo.py` | Written by us | 12 invented reports, labelled `DEMO-*`, for UI demonstration only |

### Why the official pack matters

The single most important property of this evaluation is that **the answer key is the
organisers' own file, not one we wrote**. We did not label the data we are scored on. That
removes the most common way a hackathon evaluation misleads: a team grading itself against its
own definitions.

### What the pack is not

The official pack is synthetic. It is designed to contain a realistic mix of injected anomalies
and clean records. It is **not** a sample of real 2023 polling-unit returns, and a score against
it is **not** an estimate of real-world accuracy. We say this explicitly in RESULTS.md rather
than letting the numbers imply more than they can support.

## 2. What each dataset is used to evaluate

| Component | Evaluated against | Metric |
|---|---|---|
| Deterministic rule engine | `results_synthetic.csv` + `anomaly_labels_HELD_OUT.csv` | precision, recall, F1 per rule; flag rate; clean-record false-alarm rate |
| Severity assist | `incident_reports_synthetic.csv` | held-out exact accuracy and within-one accuracy, vs a majority-class baseline |
| Claim matcher | `misinformation_claims_synthetic.jsonl` | top-1 and top-3 accuracy on deterministic paraphrases; abstention rate |
| Incident clustering | `incident_reports_synthetic.csv` | queue reduction ratio |
| Harm-ranked triage | `incident_reports_synthetic.csv` | mean severity lift of the top decile vs the rest |

## 3. Splits and why they are honest

- **Rules.** No training happens. Rules are fixed and then applied to all 900 labelled records.
  There is therefore no train/test split to leak, and the reported numbers are the numbers on the
  whole labelled set.
- **Severity assist.** A deterministic 75/25 split of the 400 incidents (first 300 train, last
  100 test). We report held-out accuracy, never training accuracy. The baseline is "always
  predict the majority training class", which is the correct honest bar for an ordinal
  classifier.
- **Claim matcher.** No training. Each claim is re-worded by a deterministic perturbation (rotate
  the words, drop one character) and the matcher must recover the original claim. A 25 % sample
  of the archive is used to keep the run fast; the sample rule is `index % 4 == 0`, so it is
  reproducible.

## 4. Label mapping — declared, not hidden

The rule engine produces findings; the official pack provides one label per record. Mapping
between them is a judgement, so we declare it in `evaluation/evaluate.py` as `RULE_TO_LABEL`
and reproduce it here:

| Rule | Official label it is meant to catch | Tier |
|---|---|---|
| `R1_accredited_exceeds_registered` | `accredited_exceeds_registered` | structural |
| `R2_sum_mismatch` | `sum_mismatch` | structural |
| `R3_digit_transposition` | `digit_transposition` | advisory |
| `R4_suspicious_round_numbers` | `suspicious_round_numbers` | advisory |
| `R5_duplicated_from_previous_unit` | `duplicated_from_previous_unit` | structural |

A reader who disagrees with a mapping can change one line and re-run; the numbers will move
accordingly, visibly.

## 5. The labelling artefact, stated plainly

The official pack assigns **one primary label per record**. But a record whose arithmetic is
broken frequently also carries a different primary label, and our rule engine will legitimately
report *both* the labelled anomaly and the arithmetic contradiction.

Under a strict "one label per record" scoring, that second, correct finding is counted as a false
positive. This depresses the headline precision in a way that does not reflect the engine being
wrong.

We therefore report **two** precision numbers, and we do not hide behind the flattering one:

1. **Label-matched precision** — the strict score against the single primary label. This is the
   conservative, comparable number and is the one quoted as the headline.
2. **Structural substantiation rate** — the share of structural findings whose stated
   contradiction actually holds in the record's own numbers, independent of the labelling
   scheme. This cannot be inflated by how the pack assigns labels.

Both are in RESULTS.md. Where they disagree, the reason is explained.

## 6. Reproducing the evaluation

```bash
# from the repository root, with the backend venv active
python evaluation/evaluate.py
```

This rewrites `evaluation/results.json`, which is the single source of every number quoted in
RESULTS.md. The evaluation is also run as part of the test suite
(`backend/tests/test_evaluation_guards.py`), which asserts that quality has not regressed and
that a heuristic we rejected stays rejected.

## 7. What this methodology cannot tell you

- It cannot tell you how the engine performs on real, messy polling-unit data.
- It cannot tell you whether the injected anomalies resemble real-world manipulation, only
  whether they match the organisers' definitions.
- It cannot tell you whether a human reviewer would agree with a given flag; that requires a
  human-factors study we have not run.
- It cannot tell you how the system behaves under load or adversarial input at national scale.

These are listed again in the "Limitations" section of RESULTS.md and in the final readiness
report.
