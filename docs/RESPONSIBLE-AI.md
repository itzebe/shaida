# Responsible AI

SHAIDA exists in a domain where an AI mistake is a public harm: telling a citizen their election was
stolen, or a polling-unit official that they cheated, is not a bug. This document states the
safeguards and, equally importantly, where the AI is **not allowed to be**.

---

## 1. The governing rule

> **SHAIDA never makes an electoral decision.** Its outputs are questions addressed to a named
> human. A model may order, shortlist or suggest. It may not conclude.

This is enforced in three independent places, so it cannot drift:

| Enforcement | Mechanism | Test |
|---|---|---|
| **By construction** | the rule engine emits findings with a tier and a message; the triage layer emits a score with a breakdown; neither emits a conclusion | `test_findings_are_ordered_structural_first` |
| **By a runtime guard** | `taxonomy.assert_no_verdict_language()` raises `VerdictLanguageError` if generated text contains verdict vocabulary | `test_no_finding_uses_verdict_language`, `test_explanations_exist_in_every_supported_language_and_avoid_verdicts` |
| **By an API-wide test** | every response is walked and asserted to contain no verdict language | `test_no_api_response_uses_verdict_language` |

## 2. Where the AI is allowed, and where it is not

| Layer | Model allowed? | Why |
|---|---|---|
| Deterministic core — rules, hash chain, triage weights, clustering, privacy floor, templates | **No** | this is the source of truth; a model here would make the truth unaccountable |
| Assistive layer — severity suggestion, claim shortlisting | **Yes, bounded** | a wrong answer here only mis-orders a queue |
| Decision layer — is this true, is this fraud, what is the result | **No, never** | there is no automated decision path in the system |

The two assistive components are deliberately the **smallest** things that do useful work — a
logistic regression and a TF-IDF retriever. Neither downloads a model, calls an API, or needs a
credential. See [`AI-METHODOLOGY.md`](AI-METHODOLOGY.md).

## 3. Abstention — the safety property that matters most

Both assistive components return an explicit *abstention* rather than a guess, and the caller must
handle it distinctly from a low value. Abstention is **tested, not assumed**:

- `test_severity_assist_abstains_when_the_posterior_is_flat`
- `test_severity_assist_abstains_when_untrained`
- `test_severity_assist_abstains_when_training_data_is_too_small`
- `test_matcher_abstains_on_unrelated_text`
- `test_matcher_abstains_when_below_the_floor_even_with_a_weak_match`
- `test_empty_archive_abstains_rather_than_crashing`

The interface shows abstention honestly — an item reads `assist: abstained (43%)`, not a fabricated
number.

## 4. No fabricated content, ever

- **Explanations are template-filled from deterministic findings**, never generated by a language
  model. A sentence about someone's evidence therefore cannot be invented.
- **No fabricated metrics, users, partnerships, testimonials or pilot results** appear anywhere in
  the documentation or the interface. Where a number is unknown (reviewer agreement, real-world
  accuracy, user counts), it is stated as unknown.
- **Multilingual strings are translated templates**, not machine translation at runtime. The About
  page states that the Hausa, Yoruba and Igbo strings are first-pass translations pending
  native-speaker review.

## 5. Uncertainty is displayed, not smoothed away

- Findings are split into a **structural** tier (arithmetic contradictions) and an **advisory** tier
  (statistical hints). Advisory findings are labelled advisory in the UI and never carry structural
  weight.
- Every finding lists the **plausible innocent explanations** a reviewer should rule out first.
- The severity assist publishes its training size and abstention behaviour.
- The evaluation reports **two** precision numbers where they diverge, quotes the conservative one
  as the headline, and records a **rejected** heuristic (49 % over-fire) so it cannot return.

## 6. Human oversight is mandatory and auditable

- The only way a report leaves the queue is `POST /v1/reports/{id}/review`, which **requires** a
  decision and a reason (`test_review_requires_a_reason`) and rejects an unknown decision
  (`test_review_rejects_unknown_decision`).
- The decision and reason are appended to the same hash-chained log (`test_review_is_recorded_and_audited`).
- The log is re-verified from stored data, not trusted from the writer, and direct-database
  tampering is proven caught.

## 7. Nonpartisanship

- No candidate or party entity exists in the schema. There is nothing to optimise for a side.
- There is **no channel through which the system can reach a voter**, so persuasion and
  microtargeting are architecturally impossible, not merely forbidden.
- The tool has no opinion about any election and cannot form one.

## 8. Alignment with the competition's red lines

| Red line | How SHAIDA complies |
|---|---|
| No auto-removal or public labelling of individuals' speech | Nothing is published automatically; no person is named; a claim gets a *shortlist of prior human labels*, never a machine label |
| No political-opinion profiling | No opinion data is collected; no user profiles exist |
| No creation of deceptive content | The tool creates no media; it hashes and verifies existing media |
| No fraud accusations | Verdict vocabulary is blocked at runtime; no fraud-determination capability exists |
| No re-identification | Identity is never collected; location is coarsened; aggregates are suppressed below a k-anonymity floor |
| No collecting reporter identity by default | There is no identity field at all |
| No location precision that endangers observers | Location is off by default and coarsened to ~1 km; sensitive categories are handled more strictly |
| No invented electoral rules or dates | The system states no rules and no dates; it computes contradictions within a record |
| No unauthorised security testing | The product is defensive only; tampering is demonstrated against our own store, in a unit test |

## 9. Known limitations of these safeguards

- The verdict-language guard is a **denylist**. It blocks known verdict vocabulary but cannot prove
  the absence of all possible judgemental phrasing. It is a strong guard, not a proof.
- Abstention protects against wrong assistive output, but it does not make the assistive model
  *fair* across languages it has never seen.
- Human oversight is only as good as the human. **No human-factors study has been run**, so we do
  not know whether reviewers agree with flags or how long review takes. This is the single largest
  gap and is stated in [`EVALUATION-REPORT.md`](EVALUATION-REPORT.md) §10.
- A prototype cannot enforce its own correct use by whoever deploys it. That is why the About page
  lists six conditions that must be met before any real use, and why winning is not deployment
  approval.
